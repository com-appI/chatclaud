**Дата аудита:** 14 ноября 2026 г.  
**Проверенная поставка:** `ChatClaud-v1.5.2-deploy-ready(1).zip`  
**Объём:** только чтение и запуск существующих проверок. Исходный проект, его зависимости и production-конфигурация не изменялись.

## 1. Объём и метод проверки

Проверен именно приложенный ZIP ChatClaud, а не предполагаемая ветка GitHub или удалённый production-сервер. Архив распакован во временную директорию, изучены `server.js`, `index.html`, `sw.js`, `package.json`, `.env.example`, каталоги `test/`, `scripts/` и имеющиеся документы проекта. По исходному коду выполнен поиск маршрутов, провайдера, промптов, лимитов, памяти и agent runtime.

Проверки выполнены локально в среде Node.js **v22.16.0**:

## 2. Краткий вывод

ChatClaud v1.5.2 — не пустой чат и не просто прокси к языковой модели. Это компактное Node.js-приложение с backend в `server.js`, крупным браузерным интерфейсом в `index.html`, интеграцией Groq, поисковым конвейером Nova, файловой базой знаний ALE и встроенным ограниченным агентным runtime.

В проекте уже есть:

- основной маршрут `/api/chat` и несколько специализированных API-маршрутов;
- Groq Chat Completions с первичной моделью `openai/gpt-oss-120b`;
- эвристический маршрутизатор задач и бюджеты agent runtime;
- внутренние модули `planner`, `runner`, `verifier`, `agent-runtime`, `tool-registry` и `flags`, встроенные в `server.js`;
- ограниченный allowlist инструментов, проверка входов и лимиты вызовов;
- локальная рабочая память одного запуска агента;
- отдельная проектная база знаний ALE;
- адаптивный поиск, извлечение страниц, дедупликация и проверка заявлений по найденным сниппетам;
- автоматизированные тесты и проверка синтаксиса.

Главный пробел — **не отсутствие agent runtime, а его частичная интеграция и недостаточная проверяемость**. Часть логики `/api/intel/run` находится за выключенным по умолчанию feature flag и отделена от основного `/api/chat`; существующий runtime не имеет формальной записи жизненного цикла задачи, пользовательской долговременной памяти, формализованного evidence store и полноценной оценки на наборе заданий.

**Рекомендация:** не заменять текущий runtime агентным фреймворком. Сначала укрепить и согласовать уже существующие механизмы небольшими изменениями, сохранив Groq, Nova, frontend API и текущую модель развёртывания.

Архив содержит **37 файлов/записей ZIP** и около **1,37 MB** распакованных данных. Это однофайловая backend-поставка: виртуальные модули `modules/intelligence/*` регистрируются непосредственно в `server.js` через `__ccDefs` и загружаются через `__ccRequire`. `package.json` сообщает версию `1.5.2`, `main: server.js`, `start: node server.js`, `test: node --test`, `check: node --check server.js && node --check sw.js && node scripts/check-inline.js`, `engines.node >=18`; разделы `dependencies` и `devDependencies` отсутствуют.

### 3.2. Главные границы

- **Frontend:** `index.html`. Браузер обращается к backend через `ccApiChat()` и другие `fetch`-вызовы. Основной frontend API ChatClaud — JSON-маршрут `/api/chat`.
- **Backend:** `server.js`, встроенный `http.createServer`, без Express.
- **Модель:** прямой серверный `fetch` в Groq OpenAI-compatible Chat Completions API. Ключи читаются из переменных окружения на сервере.
- **Поиск и страницы:** серверные вызовы Nova Browser, внутренний `runSearchPipeline`, извлечение страниц и опциональная интеграция Firecrawl при наличии ключа.
- **Долговременные данные:** локальные файлы ALE и история чатов на frontend/в Firebase (при включённом Firebase-сценарии). Это разные по назначению механизмы.

### 3.3. Backend API, обнаруженные в исходнике

Основные маршруты, перечисленные в `server.js`:

- `/api/chat` — основной чат, поиск/enrichment, выбор agent runtime и прямой вызов модели;
- `/api/fetch-url`, `/api/search` — получение страниц и поиск;
- `/api/vision`, `/api/transcribe`, `/api/video-summary` — мультимодальные/медиа операции;
- `/api/deploy` — административный deploy-функционал;
- `/api/plus/check`, `/api/plus/grant`, `/api/admin/check`, `/api/keycheck`, `/api/health` — служебные проверки и доступ;
- `/api/ale/status`, `/api/ale/start`, `/api/ale/stop`, `/api/ale/tick`, `/api/ale/search`, `/api/ale/finetune/export` — ALE;
- `/api/intel/status`, `/api/intel/run` — отдельный intelligence orchestrator, управляемый `INTEL_ORCHESTRATOR`.

Наличие маршрута не означает, что он был проверен на production или что соответствующая внешняя интеграция доступна в текущем окружении.

## 4. Состояние интеллектуального ядра

### 4.1. Intent Router и определение сложности

В `server.js` присутствуют `shouldUseCognitiveAgent()` и `estimateAgentBudget()`.

- Маршрутизация в агентный runtime основана в основном на явных флагах/режимах (`agent`, `deepResearch`, `reason`, режимы и slash-команды), эвристиках по длине запроса и наборах слов для research/complex запросов.
- Бюджет различает профили `simple`, `standard`, `research`, `deep`; для них задаются разные `maxSteps`, `maxToolCalls` и `deadlineMs`.
- В тестах проверено, что простое приветствие не запускает cognitive agent, а явная команда и один пример сложного запроса запускают.

**Пробел:** это не полный классификатор категорий, заявленных для 1.6.0. Нет подтверждённого отдельного класса для документов, программирования, математики, анализа кода и продолжения ранее начатой задачи. Продолжение сессии сейчас зависит от переданной истории сообщений, а не от устойчивого task ID и сохранённого состояния задачи.

### 4.2. Planner и execution loop

Встроенный `runAgentGraph()` реализует ограниченные переходы и action-observation. Основной cognitive flow включает brief/plan/gather, сжатие заметок, verification, synthesis и review. Он использует Groq как controller и вызывает инструментальные адаптеры.

Вторая, отдельная линия — `planner.js`/`runner.js` под `/api/intel/run`. Она формирует более шаблонный план, использует `INTEL_LIMITS` и выключена по умолчанию через `INTEL_ORCHESTRATOR`. Это не следует путать с `runCognitiveAgent()` основного `/api/chat`.

**Уже реализовано:** ограничение шагов, вызовов инструментов, времени и ранняя остановка при достаточном объёме данных; тест на достижение лимита вызовов.

**Недостаёт:** единого формального task object с `taskId`, `goal`, `status`, `createdAt`, `updatedAt`, `completionCriteria`, `completedSteps`, `failedSteps`; устойчивой записи/возобновления многошаговой задачи; явного графа зависимостей и критериев завершения, отделённых от инструкции модели.

### 4.3. Tool Registry

Виртуальный `modules/intelligence/tool-registry.js` содержит allowlist:

1. `search`;
2. `delegate_research`;
3. `fetch_url`;
4. `kb_search`;
5. `verify_claims`;
6. `calculator`.

У инструментов есть имя, описание, текстовое/ручное описание входной схемы, риск, timeout и `maxCallsPerTask`. Есть специализированная валидация входа, запрет неизвестных инструментов и лимит вызовов. Исполнители передаются в registry извне.

**Пробелы относительно целевого контракта:** формальной унифицированной `inputSchema` (например, валидируемой JSON Schema) нет; `outputSchema`, структурированного `permissions` и декларативного `errorHandling` нет; регистрация не является публичным расширяемым API; `AbortSignal` не передаётся исполнительной функции как стандартный контракт. Timeout реализован через `Promise.race`; это ограничивает ожидание результата, но само по себе не прекращает фактическую сетевую/асинхронную операцию, если handler не поддерживает отмену. Таймер registry не очищается после успешного выполнения.

Положительная граница безопасности: комментарий и код registry описывают явный allowlist без shell/admin/deploy инструментов для агента. `delegate_research` ограничен тремя параллельными поисковыми задачами; это не означает, что проект использует общую произвольную multi-agent платформу.

### 4.4. Working Memory и Long-term Memory

**Working memory:** `runAgentGraph()` создаёт in-memory state для отдельного вызова. В нём находятся план, подзадачи, заметки, пробелы, шаги, наблюдения, receipts, источники, ошибки и переходы. Состояние работает в течение текущего исполнения, но после завершения не является устойчивым объектом задачи.

**История чатов:** frontend сохраняет сессии в `localStorage`; при включённом Firebase сценарии история может сохраняться в Firestore с UID пользователя. Это сохранение транскрипта/сессии, а не отдельная семантическая память фактов или предпочтений. Правила безопасности Firestore в данном ZIP отсутствуют, поэтому корректность Firebase security rules этим аудитом не подтверждена.

**ALE knowledge base:** файловое хранилище данных/фактов проекта (например, `knowledge.json`, `queue.json`, `state.json`, evaluation log) в каталоге данных ALE. Оно служит общей проектной базе знаний и не является личной изолированной памятью каждого пользователя.

**Вывод:** обнаружена рабочая память одного запуска, frontend-история и общая база знаний. Не обнаружена отдельная opt-in долгосрочная пользовательская память с категориями предпочтений/фактов, политикой согласия, пользовательским namespace, обновлением и удалением записей.

### 4.5. Самопроверка и Evidence

Есть шаг `review` и функция проверки заявлений относительно предоставленных источников. Выполняется один review; при `revise` предусмотрен один дополнительный цикл.

Ограничения:

- review — ещё один вызов той же модели, а не независимое доказательство корректности;
- `verify_claims` назван и реализован как эвристическая проверка по предоставленным сниппетам, а не внешняя независимая проверка каждого факта;
- источники в runtime передаются как набор объектов, но не найден единый долговременный evidence record со всеми полями `sourceId/title/url/snippet/retrievedAt/sourceType/relevance/content` и явными типами «факт/предположение»;
- при ошибке разбора JSON в одном из controller/review fallback-пути есть риск слишком мягкого продолжения: некорректный review может перейти к `pass`, а некорректный ответ планировщика — быть интерпретирован как финальный текст. Это требует отдельного теста и fail-closed обработки.

Поисковый конвейер Nova уже умеет ранжировать и дедуплицировать источники, учитывать свежесть/авторитетность и формировать claim checks. Эта функциональность полезна, и её следует сохранить.

## 5. Провайдер модели и лимиты

### 5.1. Groq

`groqChat()` отправляет запросы на `https://api.groq.com/openai/v1/chat/completions`. Основная модель задаётся через `GROQ_MODEL`, по умолчанию `openai/gpt-oss-120b`. `.env.example` также документирует эту модель. При проблемах в коде предусмотрен fallback список моделей; следовательно, `GROQ_MODEL` — primary/default, но в некоторых отказных сценариях фактически может использоваться резервная модель.

Дополнительные маршруты Groq обслуживают vision и transcribe. В частности, для vision и transcription используются отдельные модельные идентификаторы/endpoint.

**Пробел:** нет самостоятельного интерфейса `ModelProvider` с `generate()`, `stream()`, `modelInfo()`, нормализацией ошибок и единым учётом usage. В ответе `groqChat()` возвращаются текст, provider-label и модель; поле `usage` из ответа Groq не включается в результат, и системного учёта prompt/completion tokens не найдено.

Необходимое ограничение для следующей версии: оставить Groq и `openai/gpt-oss-120b` как основной выбор; изменение резервных моделей, поведения fallback или production-провайдера — только отдельным решением после тестов.

### 5.2. ChatClaud quotas и провайдерные quotas

`checkRate()` реализует лимит ChatClaud по IP в памяти процесса: по умолчанию free 170 и Plus 300 обращений; после превышения порога IP блокируется на три часа, а счётчик сбрасывается после окончания блокировки. Это не скользящее трёхчасовое окно: `windowStarted` создаётся, но не участвует в регулярном сбросе счётчика. Пороговые значения настраиваются переменными `RATE_FREE_HARD`/`RATE_PLUS_HARD`. Плюс-статус разрешается через существующую проверку токена пользователя.

Это **не** лимит Groq. В коде нет доступного фактического баланса/лимита аккаунта Groq и нет отдельного формального owner quota в `checkRate()`. `rateMap` локальная для процесса: сбрасывается при перезапуске и не является распределённым счётчиком между несколькими инстансами. Такое поведение лимита нужно сверить с продуктовым намерением до изменения.

Рекомендация — ввести отдельные коды ошибок и отдельные метрики для ChatClaud quota, Groq 429/квот, сетевых отказов, timeout и tool failures, не объединяя их в одну категорию `OVERLOADED`.

## 6. HTTP, frontend и эксплуатационные риски

1. **Нет единого guard на повторную отправку HTTP-ответа.** Вспомогательная `send()` напрямую вызывает `writeHead()`/`end()`; централизованной проверки `res.headersSent`/`res.writableEnded` не найдено. В просмотренных основных ветках `/api/chat` ранние `return send()` снижают вероятность двойного ответа, но поведение при client disconnect/abort и все маршруты не покрыты отдельными тестами.
2. **Непоследовательная санитаризация ошибок.** `/api/chat` использует `publicProviderError()` для части ошибок; в `/api/transcribe` и `/api/vision` некоторые ошибки логируются как исходный `e.message` и возвращаются клиенту частично или напрямую. Требуется единая нормализация с безопасными публичными кодами.
3. **Структурное логирование неполное.** Найдена `logAgentEvent()`, но в архиве не найдено её фактических вызовов. Общие логи не предоставляют единого набора `requestId`, `taskId`, phase, toolName, duration, usage и errorCode. В нескольких местах в логи выводятся фрагменты пользовательского запроса/URL или исходные сообщения ошибок; политику минимизации данных нужно унифицировать.
4. **Нет настоящего backend token streaming.** `ccApiChat()` получает обычный HTTP response, читает `res.text()` и разбирает JSON. Название `fetchWithStream()` не соответствует transport semantics; после ответа frontend может отображать текст с typewriter-эффектом. Это не SSE/streaming tokens от Groq до пользователя.
5. **Конфликт и устаревание frontend prompt.** В `index.html` обнаружен статический текст `Сегодня 7 октября 2026 года` и подобная дата в reasoning system text. На дату аудита 14 ноября 2026 года он устарел. Там же есть указания никогда не говорить, что поиск/просмотр ссылки недоступен, тогда как серверный `CC_SYSTEM` требует честно сообщать, если поиск пустой или страница не была прочитана. Это конфликт инструкций, способный стимулировать преувеличение возможностей. Системные правила должны иметь один источник истины; текущая дата должна задаваться динамически либо не вшиваться в prompt.
6. **CORS открыт на `*`.** Это наблюдаемая настройка текущего `send()`; не утверждается, что она уже эксплуатируется. При модернизации нужно отдельно проверить, какие origins реально ожидаются и не ломает ли сужение существующих клиентов.
7. **Размер тела запроса ограничен 14 MB.** Превышение ведёт к destroy request; сценарий в сочетании с frontend timeout и client abort заслуживает smoke-теста.
8. **Временные/локальные хранилища.** `rateMap` и рабочий state агента живут в памяти процесса. ALE file store может быть ephemeral на Render без подключённого persistent disk; исходный `/api/ale/status` содержит предупреждение об этом. Не следует путать локальные файлы с гарантированной долговременной БД.

## 7. Критические пробелы перед 1.6.x

| Область | Что уже есть | Чего не хватает / что проверить |
|---|---|---|
| Intent Router | Regex/flags, профили budget | Классы задач, продолжение task, тесты на ложные срабатывания и пропуски |
| Planner | LLM-план и bounded loop; отдельный шаблонный planner | Строгая task модель, зависимости/criteria, единый путь через `/api/chat` |
| Tool Registry | Allowlist, проверка входов, timeout/call limits | Полные схемы вход/выход, permissions, AbortSignal, отмена и безопасный контракт ошибок |
| Working Memory | State одного run | Task ID, изоляция и сохранение/resume по задаче |
| Long-term Memory | История диалогов, общая ALE KB | Opt-in пользовательские записи, namespace пользователя, управление/удаление |
| Self-correction | Один review/revision | Fail-closed JSON, тесты некорректного judge, проверяемые completion criteria |

## 10. Условия готовности к реализации

Перед первой правкой необходимо подтвердить:

1. сохраняется ли deployment именно как single-file `server.js`;
2. какие Node.js версии реально поддерживает production host;
3. какой стабильный user ID/identity доступен на backend и можно ли проверить Firestore security rules;
4. какой storage доступен (Render persistent disk/Firebase/другой) и какой срок хранения допустим;
5. сохраняем ли текущий fallback список моделей или делаем строго фиксированную модель;
6. разрешено ли менять API response только additive-совместимым способом;
7. какие источники считаются достаточными для подтверждения research ответа.

**Итог аудита:** проект уже имеет зачатки Advanced Intelligence Core, но часть его компонентов разрознена, часть контрактов неформальна, а долгосрочная память и evaluation отсутствуют в требуемом виде. Безопасный следующий шаг — согласовать архитектурный план, после чего начинать только v1.6.0 небольшими patch-этапами с сохранением rollback и тестового baseline.
